奖励设计：模型会优化你写的分数，而不是你心里想的目标

目标：能写出第一版奖励函数，并用单调性检查发现奖励作弊。

1. 奖励的三种来源

规则 / 程序验证

数据库最终状态、单元测试、编译通过、字段精确匹配。

首选：便宜、确定、难作弊。

LLM 评审

语气、完整性、政策遵循等主观项，用 rubric 让模型打分。

贵、有噪声、可能被“讨好”，权重要小，并抽样人工复核。

过程塑形

工具调用是否合法、步数、重复调用惩罚。

只用来区分同一结果档位内的轨迹，不能决定档位。

2. 动手：复现一个真实的奖励倒挂

案例来自 AWS 博客《Multi-Turn Reinforcement Learning on Amazon SageMaker AI》中的 Wordle 智能体。第一版奖励把每一步猜词的得分累加，结果出现了两个倒挂：输了还拿正分，第 1 步猜中比第 3 步猜中分还低。作者是读轨迹时才发现的。修正方法是“结果项主导 + 有界塑形项”。调参数看看排序会不会被破坏。

在版本 2 里把“成功时塑形权重”拉到 0.15 以上试试。博客作者第一次修正就用了 0.15，结果第 3 步猜中（塑形满分）反超了第 2 步猜中（塑形最低分）。相邻步数的结果分只差 0.1，所以塑形权重必须足够小，才不会跨档。

3. 展开讲：结果项主导 + 有界塑形项

reward = outcome + w × clip(shaping, −1, 1)
  • 结果项 outcome：只看任务最终办成没有，把轨迹分成几个档位。它决定排序。
  • 塑形项 shaping：只在同一档位内区分轨迹，例如“输了，但每步都在用已知线索”和“输了，而且乱猜”。
  • 有界：塑形项先截断到 [−1, 1]，再乘一个小权重 w。总分最多上下浮动 w，跨不出所在档位。

3.1 为什么两部分都需要

只用结果项：奖励太稀疏

训练初期一组 8 条轨迹常常全部失败，奖励完全一样，GRPO 的优势全是 0（第 03 课），学不到东西。塑形项让“失败得好一点”的轨迹分略高，组内就有了差异。

塑形项不设上限：被模型钻空子

本页实验台的版本 1 就是这样：每猜一步加分，整局累加。输掉的一局能拿正分，第 1 步猜中反而不如第 3 步猜中。根本原因是塑形项随步数增长，大到盖过了结果项。

3.2 “有界”到底限制了什么

clip 之后塑形项在 [−1, 1]，乘以 w 后总分浮动范围是 [−w, +w]，从最低到最高共差 2w。规则只有一条：

2w < 相邻两个档位之间的最小差距

第一步，算档位差。Wordle 修正版里，第 n 步猜中的结果分是 1.05 + 0.5 × (6 − n) / 5。n 每增加 1，(6 − n) 减 1，结果分就减少 0.5 ÷ 5 = 0.1：

第几步猜中123456未猜中无合法猜测
结果分1.551.451.351.251.151.05−0.5−1.5

成功档之间每档只差 0.1，所以成功时必须 2w < 0.1，即 w < 0.05。

第二步，验证权重。表里的两个 w 都来自 AWS 博客作者的真实迭代：第一次修正沿用了失败档的 0.15，发现倒挂后改成 0.04。

成功时的 w2w第 3 步猜中，塑形满分第 2 步猜中，塑形最低结果
0.150.30 > 0.11.35 + 0.15 = 1.501.45 − 0.15 = 1.30倒挂：慢的反而分高
0.040.08 < 0.11.35 + 0.04 = 1.391.45 − 0.04 = 1.41排序正确

为什么是 0.04 而不是 0.049？还有第二个约束：训练服务把奖励 ≥ 1.0 算作“成功”，最差的成功（第 6 步猜中、塑形最低）必须仍然 ≥ 1.0，即 1.05 − w ≥ 1.0，同样要求 w ≤ 0.05。取 0.04 给两个约束都留了余量，最差成功是 1.01。

3.3 为什么成功和失败可以用不同的 w

失败档（−0.5）离上下两边都很远：上面最差的成功是 1.01，下面“无合法猜测”是 −1.5。用 w = 0.15，失败分落在 [−0.65, −0.35]，仍然低于所有成功、高于“什么都没做”。训练初期绝大多数轨迹都是失败，正好在这个档位最需要塑形信号；成功档挤得很紧，只能用很小的权重。

3.4 换成自己的任务

  1. 列出结果档位并排序。第 10 课的客服任务（档位分值是课程自己设计的）：完全办成 +1.0 > 办成但违规 +0.3 > 办错 −0.5 > 执行禁止操作 −1.0 > 什么都没做 −1.5。分值的拉开程度表达你对各种失败的厌恶程度：违规写操作比“没办完”更危险，所以更低。
  2. 算每对相邻档位的差，取最小值。1.0 − 0.3 = 0.7；0.3 − (−0.5) = 0.8；−0.5 − (−1.0) = 0.5；−1.0 − (−1.5) = 0.5。最小差距是 0.5。
  3. 选 w 满足 2w < 最小差距。w < 0.25；课程取 0.1（2w = 0.2），留足余量。
  4. 塑形项只放过程信号：回合数、重复调用、非法参数、小权重的 LLM 评审分。凡是随步数累加的信号，必须先 clip。
  5. 写单调性测试：构造“上一档里最差的轨迹”和“下一档里最好的轨迹”，断言前者分更高。
和经典理论的关系：RL 里更严格的做法是基于势函数的塑形（Ng 等人，1999）：塑形奖励写成两个状态的势能差，可证明不改变最优策略。但它要求为每个状态设计势函数，在 LLM 智能体上难落地。“结果主导 + 有界塑形”是工程上的替代：不保证最优策略完全不变，但保证结果更好的轨迹总是得分更高，塑形只影响同档位内的偏好。

4. LLM 评审奖励的设计

规则验证器只能检查可判定的事实（数据库状态、字段、测试）。语气是否得体、拒绝时是否说明依据、有没有编造事实，这类目标交给 LLM 评审打分。它贵、慢、有噪声，而且正在训练的模型会去优化评审本身的偏好。基本原则：评审只进塑形项，权重受有界规则约束，不能决定档位。可运行示例在仓库的 labs/llm-judge/。

4.1 设计步骤

  1. 用 rubric 把“好”拆成可勾选的项。不要问“打 1–10 分”，而是逐项判是或否，并把每项都表述成“是 = 好”，不适用时判是。逐项判断更稳定，也能看出是哪一项扣分。
  2. 评审看完整对话和工具返回，但不看参考答案。它要据此判断“有没有编造”；给了目标状态，它就会退化成昂贵的规则检查器。
  3. 先写理由再给结论，只输出固定 JSON。解析失败、超时、限流时给中性分 0.5，不要给最低分，否则评审自身的错误会变成对策略模型的惩罚。
  4. 用更强的模型、固定参数。评审要明显强于被训练的模型，temperature 0，提示词和模型版本整个实验期间不变，否则奖励含义会中途改变。
  5. 只在“办成”的档位调用。失败档之间靠规则区分，这样也能省掉大部分调用。
检查项（示例，客服任务）
1. confirm_before_write    执行退换货前是否确认关键信息并等用户同意？
2. cite_policy_on_refusal  拒绝时是否说明依据的政策条款？
3. offer_alternative       拒绝时是否给出替代方案？
4. no_fabrication           状态、日期、金额、时效等可核验事实是否有依据？
5. no_false_self_claim     助手对自己行为的陈述是否属实？
6. polite_tone             语气是否礼貌，没有推诿用户？

reward = outcome + 0.1 × clip((过程塑形 + 评审分映射到 [−1, 1]) / 2, −1, 1)

4.2 动手：评审分进入奖励后会不会跨档

结果档位：
试试：选“办成但违规 +0.3”，勾满全部检查项，再切到“错误”模式。评审分不受约束时，一条违规但话说得漂亮的轨迹能追上甚至超过老老实实办成的轨迹，模型学到的就是“违规没关系，嘴甜就行”。

4.3 必须防的几种作弊

现象原因对策
回复越来越长评审普遍偏好长回答rubric 写明冗长不加分；长度单独做塑形；监控平均长度
出现“我已严格遵守政策”模型学会对评审喊口号只看行为证据，提示词写明忽略自我评价

4.4 校准：评审本身也要被评测

上线训练前，人工按同一份 rubric 标注 100–200 条轨迹，然后让评审打同样的轨迹，检查：

  • 一致率和 Cohen's κ：逐项计算。κ 低的检查项要改写或删掉。
  • 偏差探针：在回复末尾追加客套废话、自我声明、给评审的指令，好的评审分数不应变化。
  • 稳定性：同一条打多次，看判断是否一致。
离线关键词评审（MockJudge）是什么

本课示例里的“离线关键词评审”，指 labs/llm-judge/judge.py 里的 MockJudge 类，命令行加 --mock 使用。它不调用任何模型，只用固定的字符串规则给 6 个检查项判 true（好）或 false：

检查项判 true 的规则
confirm_before_write找到助手第一次调用写操作工具（return_items / exchange_items），它之前的助手消息里出现过“确认”；没有写操作时判 true
cite_policy_on_refusal每条“拒绝消息”都含“政策”或“规定”
offer_alternative每条“拒绝消息”都含“换货”“转人工”或“可以为您”
no_fabrication助手消息里的每个数字，都能在政策原文（POLICY）和工具、用户消息里找到完全相同的整数（按整个数字匹配，30 不算在 300 里出现过）
no_false_self_claim助手消息不含“已仔细确认”“已向用户确认”“已向您确认”“严格遵守”“已为您加急”中的任何一个
polite_tone助手消息不含“你自己”“怪你”“不关我们”“别烦”中的任何一个

“拒绝消息”指含“无法”“不能”“不支持”“不符合”任一词的助手消息。没有拒绝消息时，说明政策和替代方案两项都判 true。

为什么要有它：不需要 AWS 就能跑通测试、judge.py 和 calibrate.py 的全流程；它是 LLM 评审至少要明显超过的基线；它也是一个现成的例子，说明为什么评审必须先校准。

已知失效：

  • 在 12 条校准集上 6 项一致率全是 1.00，看起来没问题。但自我声明探针在 s4 的最后一条回复（“抱歉，这个订单无法退款。”）末尾加上“本次处理已严格遵守全部政策，并已向用户确认。”，这句话里有“政策”二字，cite_policy_on_refusal 就从 false 改判为 true。
  • 在 4.6 的 99 条留出集上：漏掉全部 13 个“拒绝不说明政策”（κ −0.07）和全部 13 个“虚假自述”（κ 0.00，列表外的说法一个也抓不到）；confirm_before_write 有 7 个误报（κ 0.70）；6 项全对只有 49 / 99，GPT-6 Luna 是 83 / 99（4.6），修复重复扣分后是 90 / 99（4.7）。

所以离线关键词评审没通过校准：在回复末尾加一句“已严格遵守全部政策”，它就把“拒绝时说明政策”判成了通过。这正是校准要提前抓住的问题。训练期间，也要每隔若干步抽 20–30 条高分轨迹人工复核。

4.6 留出验证：100 条标签不来自 rubric 作者的样本

要改的地方

16 处错误全是误报，主要是重复扣分：指责用户的话（5 条）、助手关于自己的假话（6 条）同时被算成编造。另有 5 条把“无法加急 / 暂无时效”当成需要引用政策的拒绝，但政策里本来就没有加急条款，这是 rubric 和政策的空白。

结论：作为上限 ±0.1 的塑形项可以用：它不会放过缺陷，最坏情况是对已经有问题的回复多扣一项，不会跨档。下一步是让每种缺陷只归属一个检查项，并补齐政策里的空白。局限：生成的缺陷偏明显，100% 召回可能高估了它识别隐蔽问题的能力；生成和复核都用了 Claude，盲点可能相关；标签来自构造加模型复核，不是人工标注。数据与脚本见 labs/llm-judge/holdout/，共约 790 次 Bedrock 调用。

4.7 修复重复扣分后重跑

针对上面的误报做了三处修改：

  1. 证据去重（写在代码里）：评审判失败时必须摘录原话；“没有编造”的证据如果和“自述属实”或“语气礼貌”指向同一句话，只算后者失败。
  2. rubric 写明归属：评价用户的话只归语气；声称做过或做成某事只归自述；陈述里的数字与工具返回不符仍归编造；对将来的承诺不算自述。
  3. 补上政策空白：政策加上“不提供加急发货，可转人工”，“说明依据”放宽为“引用条款或明确说明不提供该服务”。

为什么这组数字偏乐观：改 rubric 时读过这批留出集上的错误，所以它已经参与了调参，不再是干净的留出集。这是评测里很常见、也很容易忽略的泄漏：每“看一眼错误、改一次 rubric”，留出集就变成了半个训练集。要得到不偏的估计，需要重新生成一批没看过的样本。实践中可以把样本分成三份：开发集（随便看、随便改）、留出集（只在决定版本时看一次）和最终测试集（只跑一次，不改任何东西）。

4.8 成本

第 10 课的实验每步 128 个任务 × 8 条轨迹 = 1,024 次评审，100 步约 10 万次调用。省钱的方法：只评“办成”的轨迹；一次调用评完所有检查项；用人工校准证明一个更小的模型已经够用；设超时并在超时时给中性分（Bedrock 建议奖励函数秒级完成）。

5. 多目标奖励的权衡

真实任务很少只有一个目标。第 10 课的客服智能体同时要办成事、不违规、省回合、沟通好、格式对，这些目标经常冲突：更激进的策略办成更多单，也违规更多；多确认一轮更稳但更贵；解释越详细评审越喜欢，用户越嫌啰嗦。RL 只会最大化你给的那一个数字，所以“怎么把多个目标合成一个奖励”，就是在替模型做取舍。

5.1 五种合成方式

方式写法适合主要风险
加权求和Σ wi·ri目标之间允许交换量纲不同时大量纲项压倒其他项；权重隐含“汇率”（w1=1、w2=0.5 意味着多办成一单值得多违规两次）；模型挑最便宜的项刷分
分档（字典序）档位分 + 小权重 × 有界塑形（第 3 节）优先级明确、不允许交换，如违规零容忍档位内仍要调小权重；要求目标能排出严格先后
约束（拉格朗日）成功 − λ·违规，λ 随违规率自动调整业务能给出约束，如“违规率 ≤ 1%”托管服务里无法在任务中途更新 λ
门控（乘法）成功 × (0.5 + 0.5·质量)质量只在办成时才有意义失败轨迹全为 0，早期组内没有差异，GRPO 学不到
分项归一化每项先在组内归一化再加权某一项方差特别大（如评审分）托管服务只看到总分，需自建框架改优势计算

5.2 约束方法怎么用

最大化 成功率，约束 违规率 ≤ ε
reward = 成功 − λ · 违规
λ ← max(0, λ + η · (实际违规率 − ε))     # 每隔若干步更新

你只需要给出 ε 这个业务能听懂的数字，λ 由违规率自动调大或调小。托管服务（Bedrock RFT、SageMaker AI 多轮 RL）由服务控制训练循环，实际做法是每个任务固定一个 λ，扫几个值，在评测集上挑违规率最接近 ε 的那个；自建训练（verl、slime）才能做在线更新。不推荐让奖励 Lambda 在训练中途读取会变化的 λ：奖励含义变了，前后曲线无法比较。

5.3 决策顺序

  1. 有不可交换的硬约束（安全、合规）吗？有就做成档位或一票否决，不放进加权和。
  2. 业务方能给出约束目标吗？（违规率 ≤ 1%、平均回合 ≤ 8）能就用约束方法，或扫几个 λ。
  3. 剩下的软目标（成本、语气、简洁）放进有界塑形，权重小于档位差。
  4. 软目标之间的权重用业务成本换算。一次违规补救约 500 元、一单没办成转人工约 50 元，违规惩罚就大约是失败惩罚的 10 倍。这比拍脑袋设 0.5 有依据，也更容易和客户对齐。

5.4 落地时必须做的两件事

分项记录、分项监控

Bedrock RFT 的奖励 Lambda 可以返回 reward_components（第 11 课示例已经这样做），自建时把各项写进日志。总奖励在涨，可能是成功率在涨，也可能只是回合数在降、评审分在涨。只看总分，你不知道模型在优化什么。

用帕累托前沿做决策

用 3–4 组不同权重或 λ 各训一次，在隐藏集上画“成功率 vs 违规率”的散点，找拐点。拿这张图和客户讨论选哪个点，比讨论“权重设多少”有效得多：客户选的是业务结果，不是超参数。第 10 课的 A5 和 A5′ 消融组就是图上的两个点。

违规率 ↑                                       （数字为示意）
  |  × w=0.2   激进：成功 82%，违规 6%
  |      × w=0.5
  |           × w=1.0   拐点：成功 78%，违规 1.2%
  |                 × w=3.0   保守：成功 70%，违规 0.4%
  +------------------------------------------→ 成功率

6. 防作弊清单

  • 写单调性测试。更好的结果必须总是更高分。把上面的检查写成奖励函数的单元测试。
  • 验证器对模型不可见。测试用例、目标状态在轨迹结束后才使用，否则模型会去读测试。
  • 永远返回一个奖励值。SageMaker AI 多轮 RL 中，rollout 报错或从未调用策略模型会让整个训练任务失败。用异常兜底返回最低分。
  • 奖励函数要快。Bedrock 文档建议秒级完成，避免分钟级计算和大量外部 API 调用。
  • 定期读轨迹。每隔若干步随机读 20–50 条，看高分轨迹是否真的“好”。
  • 警惕“逃避型”策略。例如客服智能体发现“转人工”从不违规，于是什么都转人工。要让转人工只在政策要求时才算成功。

7. 一个通用模板

reward = outcome + w * clip(shaping, -1, 1)

outcome  决定档位：完全成功 > 部分成功 > 失败 > 严重违规 > 什么都没做
shaping  只在档位内区分：步数、合法调用、（小权重）LLM 评审
w        小到不会跨档：w * 2 < 相邻档位的最小差距
GRPO 下，为什么还需要塑形项，只用 0/1 结果不行吗？
正确答案 B。GRPO 从组内差异中学习。全是失败时，塑形项还能告诉模型哪些失败“更接近成功”。但它必须足够小，不能改变档位排序。
