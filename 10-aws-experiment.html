AWS 实验设计：ShopOps 客服智能体

用 Amazon Bedrock AgentCore 托管智能体和环境，用 SageMaker AI 多轮 RL 训练开源模型，用 Bedrock 上的前沿模型做参照、教师和评审。

实验目标：验证多轮 RL 能否让 20–30B 开源模型在“退换货 / 改单”工单任务上接近前沿模型，同时降低政策违规率和单任务成本。
为什么选这个任务：结果可以用订单数据库的最终状态程序判定；有明确的政策约束，方便设计违规惩罚；和客户的真实场景接近。公开参照 τ²-Bench Telecom 上已有 38%→96%（SFT + RL）的结果，可以作为先验。

1. 预先登记的假设

编号假设判定标准
H1多轮 RL 能显著提升小模型的成功率隐藏集 pass^1：A4 − A1 ≥ 15 个百分点，bootstrap 95% 置信区间不含 0
H2SFT 冷启动 + RL 优于单独 RLA5 的 pass^1 高于 A4，且 pass^4 的差距更大

H4违规惩罚项能降低违规且不牺牲成功率消融组 A5′（无违规惩罚）的违规率高于 A5，成功率不显著更高

数据流：训练任务对每个 rollout 调用一次 AgentCore Runtime → 智能体通过 SageMaker Job Runtime 的 OpenAI 兼容端点调用正在训练的策略模型 → 多轮调用工具修改订单库 → 轨迹结束时计算奖励并上报 → GRPO 用组内奖励差更新 LoRA。

4. 环境与任务

  • 工具：get_user、list_orders、get_order、return_items、exchange_items、transfer_to_human。训练时工具在智能体进程内直接操作 SQLite，避免网络抖动；上线时用同样的工具签名，通过 AgentCore Gateway（MCP）接真实系统。
  • 政策文档：例如“发货超过 30 天不可退”“换货只能换同一商品的不同规格”“执行写操作前必须得到用户确认”。
  • 任务合成：参考 AgentCore RL Toolkit“从环境本身合成可验证任务”的方法，用 Bedrock 上的前沿模型基于数据库状态和政策生成任务、用户画像和目标最终状态；人工抽检 10%。
  • 用户模拟器：对话中的“用户”由一个固定的模型扮演（固定 temperature 和 seed），所有组共用，避免引入组间差异。
  • 数据切分：600 训练 / 150 验证 / 200 隐藏测试。隐藏集使用不同的用户和订单，其中 30% 是训练中没出现过的政策组合；实验开始前冻结并记录 SHA256。

5. 奖励函数

reward = outcome + 0.1 * clip(shaping, -1, 1)

outcome（决定档位）
  +1.0  最终数据库状态与目标一致，且无违规
  +0.3  状态一致但有违规（例如未确认就执行）
  -0.5  状态不一致（办错或没办完）
  -1.0  执行了政策禁止的写操作
  -1.5  从未产生合法工具调用

shaping（只在同一档位内区分）
  + 回合数少于中位数              - 重复调用同一个只读工具
  - 非法参数或不存在的订单号        + （小权重）LLM 评审给的沟通质量分

上线前按第 04 课的方法写单调性测试：任何“完全成功”的得分高于任何“状态一致但违规”，后者又高于任何“办错”，且所有失败轨迹得分都小于 0。塑形权重 0.1 × 2 = 0.2 小于最小档位差 0.5，不会跨档。

6. 智能体代码骨架（训练和部署共用）

from bedrock_agentcore import BedrockAgentCoreApp
from strands import Agent
# sagemaker_rft_handler、build_model 的导入方式以 aws-samples/sample-multi-turn-rl-wordle 为准

app = BedrockAgentCoreApp()

@app.entrypoint            # 必须在最外层，负责启动 HTTP 服务；否则每次调用 30 秒超时
@sagemaker_rft_handler     # 把返回的 reward 上报给 SageMaker AI
def handle_rollout(payload):
    task = parse_task(payload["prompt"])           # 任务 JSON：用户画像、目标状态、id
    env = ShopEnv.from_snapshot(task["db_seed"])   # 每个 rollout 一份独立的 SQLite
    try:
        agent = Agent(model=build_model(),          # 指向正在训练的策略模型
                      system_prompt=POLICY_PROMPT,
                      tools=env.tools())
        run_dialog(agent, UserSimulator(task), max_turns=20)
        return {"reward": score(env, task)}         # 规则验证 + 有界塑形
    except Exception:
        return {"reward": -1.5}                     # 永远返回奖励，否则整个训练任务会失败

7. 指标

指标定义用途
pass^1隐藏集单次成功率，temperature 按服务设置主指标
pass^4同一任务跑 4 次全部成功的比例稳定性；客服场景比 pass@k 更重要
违规率出现任何政策违规的轨迹占比安全性
完成率正常结束（未超时、未崩溃）的轨迹占比，单独报告避免把“没跑完”算成“能力差”
平均回合数 / token 数 / p50 延迟来自 AgentCore traces效率
每千任务成本推理 token 成本 + Runtime 费用验证 H3

统计方法：每组在隐藏集上跑 3 次（不同 seed），报告均值和 bootstrap 95% 置信区间；RL 组至少跑 2 个独立训练种子。

8. 执行步骤（约 3 周）

第 1 周 · 环境：实现 ShopEnv、工具、政策、奖励函数和单调性测试；用 Bedrock 前沿模型合成任务并人工抽检；本地跑通 A0 和 A1 各 20 条。
部署与冒烟测试：创建两个 IAM 角色。训练任务角色信任 job.sagemaker.amazonaws.com，同时允许 sts:AssumeRole 和 sts:TagSession；Runtime 角色附加 AmazonSageMakerJobRuntimeAccess。执行 agentcore deploy，用带假 job ARN 的 payload 做冒烟测试，日志里出现 “Could not find job” 说明链路是通的。
第 2 周 · 基线、SFT 与 RL：用评测任务跑 A0、A1、A2；收集 A0 的成功轨迹训练 A3；启动 A4、A5、A5′ 的多轮 RL 任务，先用 100 步、每步 128×8 的规模。在 MLflow 盯 val/reward/pass_at_1、奖励方差和有效工具调用率。训练期间不要重新部署智能体，否则整个任务会失败。
第 3 周 · 评测与分析：所有组在冻结的隐藏集上按服务参数评测 3 次；每组读 30 条失败轨迹做错误分类；出报告。

10. B 线：完全自建（需要全参数或算法消融时）

同一份 Strands 智能体仍然部署在 AgentCore Runtime，用开源的 AgentCore RL Toolkit（pip install 'agentcore-rl-toolkit[core]'）把模型调用接到它的 rollout 网关，训练后端选 verl 或 slime，跑在 SageMaker HyperPod 或 Amazon EKS 的 GPU 集群上。这条线还能做：

  • GRPO、DAPO、GSPO 的算法消融；
  • 全参数与 LoRA 对比；
  • 同步与异步 rollout 的每 GPU 小时收益对比；
  • 以 A3 的 SFT 检查点为起点做 RL。

代价：需要自己管理 GPU 集群、权重同步、vLLM / SGLang 服务和训练稳定性。

11. 风险与对策

风险对策
奖励作弊，例如什么都转人工以规避违规对 transfer_to_human 设条件化奖励：只有政策要求转人工时才算成功
工具调用格式漂移，梯度消失降低学习率；从纯文本中恢复工具调用并给小幅格式惩罚；监控有效调用率
高并发下凭证刷新失败（403）使用单个可自动刷新的会话、短缓存，遇到 403 时重新签名（博客中的踩坑）
验证曲线低估真实能力按服务时的 temperature 和推理强度单独跑评测任务
任务泄漏或训练数据污染隐藏集在训练前冻结；合成任务与公开 benchmark 去重
用户模拟器偏差所有组共用同一个模拟器；隐藏集再换一个模拟器复测一次
