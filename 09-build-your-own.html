客户自建：路线、选型与成本

目标：能判断一个客户任务适不适合做 RL，该走托管还是自建，环境和评测要花多少人力，同一份工作量在不同路线上大概花多少钱，以及前 90 天每两周交付什么。本页的产品和价格事实都核对于 2026-11-11，来源见第 14 节；查不到一手来源的写“未核实”或者不写。工作量估算是本课程的经验假设，页面上都单独标了出来。

本页和第 08 课第 3 节（托管方案对比）、第 6 节（选型助手）用同一套事实和逻辑。托管服务的模型清单、区域和价格经常变化，落地前请重新打开第 14 节的链接核对。

2. P0 就绪度评分卡：这个任务该不该做 RL

先回答 8 个问题。每题 0–2 分，满分 16。有些答案是硬阻断：不管总分多少，都会直接给出“先修复”或“暂不建议 RL”。判断依据来自 Bedrock RFT 的最佳实践（基线一直为 0 先做 SFT，高于 95% 可能不需要 RFT；先用 100–200 条样本验证奖励）和第 04、07 课。

请回答全部 8 个问题。
为什么基线要在 5%–95% 之间：GRPO 靠同一任务多条轨迹之间的奖励差来学习（第 03 课）。基线接近 0，一组 8 条几乎全失败，没有差异可学；基线接近 100%，几乎全成功，同样没有差异，提升空间也小。第 11 课用按字段给部分分的方式，把“全错 / 全对”拆成有梯度的分数，就是为了处理前一种情况。

3. 自建路线图（不管走哪条路都要经过）

P0 适配性评估（约 1–2 周）：用第 2 节的评分卡。任务能否自动判定成功？基础模型基线成功率是否在 5%–95% 之间？是否有几百到几千个多样的任务？有硬阻断，先别做 RL。
P1 环境工程（2–4 周，工作量最大）：可复位的沙箱、模拟或只读的工具后端、任务生成器、对模型隐藏的验证器。不能直接拿生产系统给 RL 打：上千条并发轨迹会压垮下游，而且写操作有真实副作用。第 4 节有清单和工作量估算器。
P2 奖励函数（约 1 周，持续迭代）：结果主导 + 有界塑形；为奖励写单调性测试；人工读 50 条轨迹。用 LLM 评审时，先按第 04 课第 4.4–4.8 节做校准、留出验证和最终测试。
P3 冷启动 SFT（按需）：用前沿模型跑出成功轨迹做蒸馏，修复格式和基本能力。基线接近 0 时这一步通常是必须的。
P4 RL 训练：从小规模开始（Bedrock 文档建议先用 100–200 条样本验证奖励函数是否正确）；group size 8–16 是常见取值；监控奖励均值与方差、熵、有效工具调用率、轨迹长度。训练期间不要重新部署智能体（第 07 课第 8 节）。
P5 评测：开发集、留出集、最终测试集三份分开，评测前冻结；按实际服务时的解码参数评测；报告 pass^k 衡量稳定性；完成率单独报告。第 5 节有完整协议。
P6 部署与持续学习：线上 trace 回流生成新任务；训练和部署用同一份智能体代码，避免“训的不是上线的”。SageMaker AI 多轮 RL 的发布公告写明，训练后的模型可以部署到 SageMaker AI 端点或 Amazon Bedrock。

4. 环境工程：最大的一笔投入

RL 训练里，模型每一步都要和环境交互。环境要同时满足三件事：每条轨迹互不干扰、上千条并发时不出故障、模型看不到判分答案。第 10 课的 ShopEnv 是一个完整例子：6 个工具（3 个只读：get_user、list_orders、get_order；3 个写：return_items、exchange_items、transfer_to_human），每条 rollout 从一份独立的 SQLite 快照启动，工具在进程内直接操作数据库，任务由前沿模型基于数据库状态和政策合成、人工抽检 10%，判分看最终数据库状态。

可靠性是环境的一部分。第 07 课第 8 节的规则：每条 rollout 都要在有限时间内结束并返回一个奖励；区分模型的错和环境的错；下游限流；凭证在并发下会被打满。GRPO 按组计算优势，单条失败率 1% 时，G = 8 的一组全部正常的概率是 0.998 ≈ 92.3%，失败率 5% 时只有 66.3%。所以估算器里“可靠性加固”是固定项，不能省。

5. 评测协议

评测决定了“RL 有没有用”这个结论是否可信。下面的协议和第 10 课的实验设计一致。

集合用途规则第 10 课的取值
开发集调提示词、调奖励、读错误随便看、随便改训练 600 / 验证 150
留出集决定版本（选检查点、选 rubric）只在做决定时看；每看一次错误再改，它就变成半个训练集150
最终测试集报告结论训练前冻结并记录 SHA256；只跑一次；看完结果不改任何东西；最好换一个数据来源隐藏 200，其中 30% 是训练中没出现过的政策组合
  • 先冻结再跑：评测集、判分代码、智能体配置、解码参数都记录哈希，再开始跑。
  • 按服务设置评测：temperature、推理强度、最大回合数都和上线一致。Wordle 博客里，gpt-oss-20b 在训练用的 low 推理强度下从 15% 到 69%，在默认推理强度下从 61% 到 84%，两组数字差别很大，只有和上线一致的那组有意义。
  • 报告 pass^k：同一任务跑 k 次全部成功的比例。客服、运维这类场景要的是“每次都对”。
  • 完成率单独报告：超时、崩溃、空输出不要悄悄剔除，也不要和“答错”混在一起。
  • 统计：多个种子、bootstrap 置信区间；RL 组至少两个独立训练种子（第 10 课第 7、8 节）。

5.2 动手：同样的 pass^1，不同的稳定性

每行一个任务，每个字符是一次试验：1 成功，0 失败，x 没跑完（超时、崩溃）。pass^k 按每个任务 c 次成功、n 次试验，用无偏估计 C(c, k) / C(n, k) 再对任务求平均；x 在 pass^k 里算失败。

6. 成本估算器（托管多轮 RL，按 token 计费）

默认值取自 AWS 博客公开的 Wordle 实验（gpt-oss-20b，博客写明的 us-east-1 列表价，博客发布于 2026-10）：100 步，每步 128 个任务 × 8 条轨迹；博客报告的总量是 105,486 条 rollout、4.92 亿 prefill、1.60 亿生成、6.43 亿训练 token，折合每条轨迹约 4,660 prefill、1,514 生成、6,099 训练 token。换成你的任务估计值。

训练 token 成本通常最大，并且随轨迹长度增长。缩短轨迹（限制回合数、截断旧工具输出、降低推理强度）是最直接的省钱方式。博客中 low 推理强度比 medium 少用 63%–83% 的生成 token。默认值算出的总轨迹数是 100 × 128 × 8 = 102,400，比博客实际的 105,486 条少约 3%，所以合计约 $405，略低于博客的训练 token $339 + Runtime 约 $79。

7. 同一份工作量，在四条路线上大概花多少

这个对比器直接读取第 6 节的工作量（轨迹数、每条 token 数、token 单价、Runtime 单价），再分别按四条路线的计费方式计算。只算云账单，不算人力。环境工程（第 4 节）和评测（第 5 节）在每条路线上都要做，所以不进入对比；自建额外的 GPU 运维人力单独列在第 9 节。

每条路线的口径
  • SageMaker AI 多轮 RL：按百万 token 分预填充、生成、训练三项计费，AgentCore Runtime 按 vCPU 和内存另计。
  • Bedrock RFT：整个训练流程按小时计费，gpt-oss-20b 和 Qwen3 32B 均为 80 美元 / 训练小时（us-east-1、us-west-2），训练后的模型存储 1.95 美元 / 月，推理按 token 另计。官方没有公布“多少数据需要多少训练小时”，10 小时只是示例假设，请用 100–200 条样本的小规模试跑实测。它只支持单次回答，多轮任务要先改写成单轮才可比。
  • SageMaker AI 训练会话 API：也按预填充、生成、训练三类 token 计费，但文档没有给出单价，本页没有核实到具体数字，所以不计算。
  • HyperPod / EKS 自建：HyperPod 按“所分配容量的时长”计费，账单按分配类型、实例类型和使用时长分项。集群开着调试、排队、等数据的时间都要付钱，所以填的是分配时长，不是训练时长。本页不写死实例价格，请自己查定价页并注明日期。EKS、FSx for Lustre、S3 等另计。
怎么读结果

默认值下，托管多轮 RL 的 token 费用约 $329，Runtime 约 $77；Bedrock RFT 是 10 × $80 + $1.95 ≈ $802（如果任务能改写成单轮）；自建要先填节点单价。对比器会算出盈亏平衡单价：1 个节点分配 24 小时，节点单价低于约 $13.69 / 小时，自建的云账单才比托管训练 token 便宜。这个比较还没有算 GPU 运维人力。

托管多轮 RL 和自建都把 rollout 放在 AgentCore Runtime，所以 Runtime 费用两边相同。AgentCore 定价页的 Runtime 示例按 $0.1276 / vCPU 小时、$0.0169 / GB 小时计算（页面示例，未注明区域，2026-11-11 查看）；CPU 在等待 LLM 和工具返回时不计费。默认 $0.75 / 千条轨迹是 Wordle 博客的约 $79 / 105,486 条折算，轨迹越长、内存越大，单价越高。

8. 自建 GPU 的经验量级（仅供估算）

  • ≤32B 模型做 LoRA RL：单节点 8×H100/H200 级别通常可以起步，推理和训练共置（经验值，未核实到官方配置表）。
  • 30B–70B 全参数或大 MoE：通常 2–8 个节点，推理和训练分离部署（经验值）。
  • 两个有出处的参照：AgentCore RL Toolkit 报告 Qwen3 Coder 30B 在一个 p6 节点上约有 500 万 token 的 KV 容量，按 64K 上下文只能放 78 条轨迹（第 07 课第 7 节）；verl README 收录了 Mind Lab 在 64 张 H800 上对万亿参数模型做 GRPO LoRA 的案例（第 08 课）。
  • Rollout 沙箱是 CPU 资源，单独弹性扩缩；SWE 类任务上千并发很常见。AgentCore Runtime 每会话最多 2 vCPU / 8 GB，活跃会话默认配额在美东（弗吉尼亚北部）和美西（俄勒冈）为 5000（第 07 课第 9 节）。
  • HyperPod 按分配时长计费：训练跑完要及时缩容，调试阶段用小集群。
  • 实际需求和轨迹长度、上下文长度、并行策略强相关，一定先做小规模压测。
团队配置
  • 环境工程师 1–2 人：沙箱、工具模拟、任务生成。最容易被低估。
  • RL / 训练工程师 1 人：托管路线可以兼职。
  • 领域专家：定义成功标准、审轨迹。
  • 评测负责人：隐藏集、统计显著性、防数据污染。
  • 自建还要加：GPU 集群运维（调度、故障节点、存储、权重同步、vLLM / SGLang 服务），通常至少 1 人。

12. 客户常问

我们已经有在线跑的智能体，能直接用线上数据训练吗？

线上 trace 适合用来生成任务和做 SFT，但不能直接当 RL 数据：RL 需要用当前策略重新和环境交互。正确做法是把线上会话转成“初始状态 + 目标”的任务，在沙箱环境里重放。

RL 会不会让模型通用能力下降？

可能会，尤其是全参数训练和高学习率。LoRA、KL 约束、混入通用任务、在通用基准上做回归测试，都可以控制这个风险。

多久能看到效果？

托管路线下，环境和奖励就绪后，一次训练通常是小时级（Wordle 示例 100 步约 12 小时 40 分钟）。真正的时间成本在 P1 环境工程，第 10 节的计划里它占了 4 周。

和提示词工程、SFT 比，RL 的边界在哪？

先做提示词优化和 SFT，它们更便宜。RL 适合“知道什么是好结果，但说不清正确步骤”的任务，以及需要在稳定性（pass^k）上进一步提升的场景。

我们在用 OpenAI 的 RFT，还能继续规划吗？

不建议。OpenAI 的 Deprecations 页面写明：2026-05-07 起从没跑过微调的组织不能再建任务；2026-07-02 起过去 60 天没调用过微调模型的组织也不能；2027-01-06 起现有活跃客户也不能再建新任务，已训练模型的推理保留到底座模型下线。RFT 的主力模型 o4-mini 已于 2026-10-23 下线。迁移时环境、奖励和评测可以复用，训练换到第 9 节表里的路线。

只用 LoRA 够吗？

目前 AWS 的托管多轮 RL 只训练 LoRA，训练会话 API 的文档示例也用 LoRA 客户端。大多数“把小模型在一个业务任务上练稳”的场景，LoRA 是合理的起点。需要全参数时走自建，并在第 10 节第 9–10 周的消融里比较两者。

团队读了留出集上的评审错误，改了 rubric，在同一个留出集上重跑，一致率从 0.89 升到 0.98。最准确的说法是？
