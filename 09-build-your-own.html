2. 自建路线图（不管走哪条路都要经过）

P0 适配性评估（约 1 周）：任务能否自动判定成功？基础模型基线成功率是否在 5%–95% 之间？是否有几百到几千个多样的任务？任何一个答案是“否”，先别做 RL。
P1 环境工程（2–4 周，工作量最大）：可复位的沙箱、模拟或只读的工具后端、任务生成器、对模型隐藏的验证器。不能直接拿生产系统给 RL 打：上千条并发轨迹会压垮下游，而且写操作有真实副作用。
P2 奖励函数（约 1 周，持续迭代）：结果主导 + 有界塑形；为奖励写单调性测试；人工读 50 条轨迹。
P3 冷启动 SFT（按需）：用前沿模型跑出成功轨迹做蒸馏，修复格式和基本能力。
P4 RL 训练：从小规模开始（Bedrock 建议先用 100–200 条样本验证奖励）；group size 8–16；监控奖励均值与方差、熵、有效工具调用率、轨迹长度。
P5 评测：独立的隐藏测试集；按实际服务时的解码参数评测；报告 pass^k 衡量稳定性；完成率单独报告。
P6 部署与持续学习：线上 trace 回流生成新任务；训练和部署用同一份智能体代码，避免“训的不是上线的”。

3. 成本估算器（托管多轮 RL，按 token 计费）

默认值取自 AWS 博客公开的 Wordle 实验（gpt-oss-20b，us-east-1 发布时的列表价）：100 步，每步 128 个任务 × 8 条轨迹，平均每条轨迹约 4.7k prefill、1.5k 生成、6.1k 训练 token。换成你的任务估计值。

训练 token 成本通常最大，并且随轨迹长度增长。缩短轨迹（限制回合数、截断旧工具输出、降低推理强度）是最直接的省钱方式。博客中 low 推理强度比 medium 少用 63%–83% 的生成 token。

4. 自建 GPU 的经验量级（仅供估算）

  • ≤32B 模型做 LoRA RL：单节点 8×H100/H200 级别通常可以起步，推理和训练共置。
  • 30B–70B 全参数或大 MoE：通常 2–8 个节点，推理和训练分离部署。
  • Rollout 沙箱是 CPU 资源，单独弹性扩缩；SWE 类任务上千并发很常见。
  • 实际需求和轨迹长度、上下文长度、并行策略强相关，一定先做小规模压测。
团队配置
  • 环境工程师 1–2 人：沙箱、工具模拟、任务生成。最容易被低估。
  • RL / 训练工程师 1 人：托管路线可以兼职。
  • 领域专家：定义成功标准、审轨迹。
  • 评测负责人：隐藏集、统计显著性、防数据污染。

5. 客户常问

我们已经有在线跑的智能体，能直接用线上数据训练吗？

线上 trace 适合用来生成任务和做 SFT，但不能直接当 RL 数据：RL 需要用当前策略重新和环境交互。正确做法是把线上会话转成“初始状态 + 目标”的任务，在沙箱环境里重放。

RL 会不会让模型通用能力下降？

可能会，尤其是全参数训练和高学习率。LoRA、KL 约束、混入通用任务、在通用基准上做回归测试，都可以控制这个风险。

多久能看到效果？

托管路线下，环境和奖励就绪后，一次训练通常是小时级（Wordle 示例约 12.7 小时）。真正的时间成本在 P1 环境工程。

和提示词工程、SFT 比，RL 的边界在哪？

先做提示词优化和 SFT，它们更便宜。RL 适合“知道什么是好结果，但说不清正确步骤”的任务，以及需要在稳定性（pass^k）上进一步提升的场景。
