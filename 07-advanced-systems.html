系统架构与异步 Rollout

目标：知道一个 Agentic RL 系统由哪些组件组成，各自跑在什么资源上，一步训练的时间花在哪里，为什么异步很重要、代价是什么，以及怎么估算需要多少沙箱和多大带宽。本课的计算器都用同一个示例任务：每步 32 道题 × 每题 8 条轨迹，每条平均 20 回合。

2. 动手：同步和异步，GPU 在等什么

智能体任务的轨迹长度通常是长尾分布：有的 3 轮就结束，有的要 40 轮。同步模式下整批都要等最慢的那条；异步模式让训练和下一批采样重叠。AgentCore RL Toolkit 公开的 SWE-Gym 实验（Qwen3 Coder 30B）里，“异步 + 每步 2 个 mini-batch”的配置按每 GPU 小时的奖励提升比同步基线高约 22%（1.22 倍）；但“异步 + 每步 1 个 mini-batch”只有 0.98 倍，因为吞吐涨了、每个优化步的奖励提升却变慢了。AReaL、slime、SkyRL 都把异步作为核心设计。代价是数据变成 off-policy，需要第 06 课第 8 节讲的修正（本课第 5 节给出具体比例）。

3. 一步训练的时间花在哪

先用一个具体例子把一步拆开。同步模式下一步分三段：rollout（所有轨迹跑完，等最慢的那条）、训练（对所有 token 做前向和反向）、权重同步（把新权重推给推理引擎）。下面每个输入都是示例值，换成你自己测到的数。

每回合时长   = 每回合生成 token / 单序列生成速度 + 每回合工具延迟
平均轨迹时长 = 回合数 × 每回合时长
rollout 阶段 = 平均轨迹时长 × (最慢 / 平均)          # 同步要等最慢的一条，倍数见第 4 节
训练 token 数 = 轨迹数 × 回合数 × (生成 token + 环境 token)   # 环境 token 不算损失（mask），但要做前向和反向
训练阶段     = 训练 token 数 / (每卡训练吞吐 × 训练卡数)
权重同步     = 参数量 × 2 字节 (bf16) / 带宽                # 第 6 节细算
默认例子：256 条轨迹，每回合 400/40 = 10 秒生成 + 2 秒工具 = 12 秒，平均一条 240 秒。同步要等最慢的那条，按第 4 节默认分布约是平均的 3.8 倍，rollout 阶段 912 秒。训练 256 × 20 × 1400 = 716.8 万 token，16 张卡每卡 2500 token/秒，179.2 秒。30B 参数 bf16 共 60 GB，按 25 GB/秒同步要 2.4 秒。一步合计 1093.6 秒，其中 rollout 占 83%。如果没有长尾（倍数为 1），一步只要 421.6 秒。这说明在这个例子里，优化的第一目标是长尾等待，而不是训练速度或带宽。

这是粗估：忽略了预填充（prefill）的计算、奖励计算时间和调度开销；单序列生成速度在并发变化时也会变（并发低时单条更快，但总吞吐更低）。每卡训练吞吐和生成速度都是示例假设，不同模型、硬件和并行策略差别很大，请用自己的 profiler 实测。

还要注意一点：多轮任务不一定是 rollout 瓶颈。AgentCore RL Toolkit 的 SWE-Gym 报告指出，推理端对环境 token 是并行预填充（快），对智能体生成的 token 是逐个解码（慢）；训练端对两种 token 都并行做前向和反向。他们观察到平均轨迹里只有约 20% 的 token 来自智能体，在这种比例下推理和训练每卡吞吐大致相当，所以选了 1:1 的训练卡和推理卡比例。把上面的“每回合环境 token”调大，可以看到训练阶段的占比随之上升。

4. 长尾：同步模式为什么要等那么久

同步模式下，一批 N 条轨迹并发跑，rollout 阶段的时长由最长的那一条决定。最大值随 N 增长，平均值不变，所以批越大，等待越久。这里用对数正态分布模拟轨迹时长（把均值归一化为 1）：σ 越大，尾巴越长。σ 只是示例参数，请用自己任务的轨迹时长分布替换。

批内并发槽空闲比例 = 1 − Σ L_i / (N × max L_i) = 1 − 平均 / 最大
曲线显示的批大小 N：
一批里仍在运行的轨迹比例随时间的变化（横轴以平均时长为 1）
默认 σ = 0.5、N = 256 时，一批中最长轨迹的期望约为平均的 3.8 倍（第 3 节用的就是这个值），并发槽有约 72% 的时间在空等。N 从 8 增加到 1024，倍数从约 1.9 增加到约 4.6。最大值的增长大致与 exp(σ·√(2 ln N)) 同阶（这是渐近趋势，不是精确值），所以批越大越吃亏。截断能把空等降下来，但被截断的轨迹没有自然结束，奖励要按第 8 节的规则处理。

“并发槽空闲”和“GPU 空闲”不是一回事。推理吞吐随并发增长但会饱和，并发从 256 降到 20 时，GPU 不会空闲 92%，而是从高效的大批解码退化成低效的小批解码。AgentCore RL Toolkit 的报告里，同步基线每个推理副本的平均并发只有约 11，KV cache 平均利用率低于 25%；改成异步后平均并发约 34 到 38，吞吐提高到 1.38 到 1.42 倍。AReaL 论文也把“生成必须等最长的输出完成”列为同步系统 GPU 利用率低的主要原因。

5. 异步与陈旧度：有多少 token 来自旧策略

异步系统让 rollout 不停地跑，训练凑够一批就更新，于是一个训练批里混有不同版本权重生成的数据。陈旧度 = 训练时的策略版本 − 生成这个 token 的版本。几个系统的做法：

  • AReaL：用超参数 η 限制最大陈旧度。当前版本为 i、已提交 Nr 条轨迹、训练批大小 B 时，只有满足 ⌊(Nr − 1)/B⌋ ≤ i + η 才提交新的生成请求；η = 0 就退化为同步 RL。组批时优先取较旧的轨迹。论文实验中代码任务用 η = 4，数学任务用 η = 8，推理卡和训练卡按 3:1 分配。
  • 可中断生成（partial rollout）：AReaL 的 rollout worker 收到新权重时会中断正在生成的序列，丢弃旧权重算出的 KV cache，用新权重重算后继续解码。于是一条轨迹由多个版本的片段组成。论文用解耦 PPO 目标处理：区分采样用的行为策略 πbehav 和作为信任域中心的近端策略 πprox，并证明分段生成仍等价于从某个行为策略采样。
  • slime：把训练（Megatron）、rollout（SGLang）和数据缓冲区解耦，仓库里的 fully_async 示例就是为“部分样本比其他样本长得多”的智能体场景准备的。
  • SkyRL-Agent：重点在 rollout 内部的调度：把每条轨迹拆成运行时初始化、智能体运行、奖励计算三个阶段，用三个有界队列让 CPU 阶段和 GPU 推理重叠。论文报告这种异步流水线比朴素的有界异步批处理快约 1.55 倍，生成阶段 GPU 利用率稳定在约 90%。

下面的模拟按 AReaL 的规则限制提交速度：64 个 rollout 槽，每步训练 64 条轨迹，轨迹时长服从第 4 节的对数正态分布（平均 100 个时间单位，σ = 0.5），训练一步耗时可调，权重同步视为瞬间完成。它统计被训练的每个 token 的陈旧度。

默认 k = 2、不可中断：rollout 槽一直满载，每单位时间完成的训练步数是同步（k = 0）的约 3.6 倍；代价是只有约 0.2% 的 token 是严格同策略的，约 34% 落后 1 个版本，约 50% 落后 2 个，约 3% 落后 4 个以上。最长的轨迹会落后到 8 个版本：AReaL 的规则限制的是提交，一条很长的轨迹跑完时已经过了好几次更新，所以 AReaL 还要在组批时控制陈旧度。勾上“可中断生成”，同策略 token 升到约 9%，落后 4 个以上降到约 0.5%，代价是每次中断都要重算 KV cache（模拟里没有计入）。把 k 调到 0 就是同步：全部同策略，槽利用率只有约 28%。

和第 06 课第 8 节连起来：那里的简化例子假设每个版本让某个 token 的 log 概率同向变化 δ，落后 s 个版本后 ρ = es·δ。δ = 0.05 时，s = 4 就有 ρ = 1.22，超过 1 + ε = 1.2，A > 0 的这类 token 会被 clip 掉梯度。上面计算器里“落后 4 个以上”的比例，就是在这个简化假设下会失去梯度的 token 比例的上限估计。实际系统中常用的修正是截断重要性采样或掩码：AgentCore RL Toolkit 的 SWE-Gym 报告用了 verl 的 rollout correction（token 级比率、掩码阈值 2、decoupled 模式），在每步 2 个 mini-batch 的配置里，训练后期最多约 3% 的 token 被掩码。他们的结论是稳定性仍需持续监控，更长的训练可能需要更多对策。

6. 资源怎么分：共置还是分离

组件资源类型扩缩特点
Rollout 工作池（智能体 + 沙箱）CPU、内存、磁盘并发量大（数百到数千），按需弹性；适合 serverless 或 K8s
推理引擎GPU吞吐决定采样速度；需要支持热更新权重
训练引擎GPU按模型大小和并行策略固定；可与推理共置（colocate）或分离
奖励服务CPU（LLM 评审时调用外部模型）要快；Lambda 天然并行
共置（同一批 GPU 轮流做推理和训练）省卡但有切换开销；分离部署让推理和训练同时跑，但需要跨机权重同步，还要定好两边的卡数比例。verl 的 HybridFlow 论文设计了 3D-HybridEngine，在同一批卡上把 actor 模型在训练和生成两种并行布局之间重新切分（resharding），做到零显存冗余并减少通信；AReaL、slime 等框架更强调分离和异步。

6.1 权重同步要多久

分离部署每一步都要把新权重从训练卡传到推理卡。最简单的估算是“字节数 / 带宽”。下面的带宽预设是示例假设，不是某款硬件的规格；实际有效带宽取决于网卡数量、拓扑、通信库和是否与计算重叠，请实测。

同步时间 ≈ 参数量 × 每参数字节数 / 有效带宽
30B × 2 字节 (bf16) = 60 GB;  60 GB / 25 GB/秒 = 2.4 秒      # 1 GB/秒 = 8 Gb/秒

在第 3 节的例子里，跨机同步 2.4 秒只占一步的 0.2%，并不是瓶颈；共置如果每次切换（训练状态卸载、推理权重和 KV cache 重新加载、重新切分）要 20 秒，一步两次就是 40 秒，约占 3.7%。这两个开销都远小于长尾等待。所以选共置还是分离，主要看的是能不能让 rollout 和训练重叠，而不是带宽。

共置更合适分离更合适
规模卡少、模型小，单独留一批推理卡会让任一边吃不饱卡多，两边都能各自喂饱
轨迹长度分布轨迹短、长度整齐，同步等待不严重长尾严重，需要异步把等待藏起来
训练方式严格同策略、调试阶段（行为更容易复现）能接受有界陈旧度并做离策略修正
主要成本每步两次切换；rollout 时训练状态要腾出显存跨机权重同步；推理卡和训练卡的比例要调（AReaL 用 3:1，AgentCore RL Toolkit 的 SWE-Gym 实验用 1:1）

减少同步量的做法：只训 LoRA 时只传适配器；slime 支持只发送变化了的权重字节（Delta Weight Sync，经共享存储），也支持连接训练任务之外管理的推理服务、通过磁盘在不同 GPU 集群之间更新；slime 生态中的 Relax 用 NCCL 广播把新权重异步推给 rollout，并和下一步训练重叠。

7. 要多少个沙箱：用 Little 定律估并发

排队论里的 Little 定律：系统里平均同时存在的任务数 = 到达（完成）速率 × 每个任务的平均停留时间。放到 rollout 上：

需要的并发会话数 = 目标吞吐（条/秒）× 平均轨迹时长（秒）
2000 条/小时 × 240 秒 / 3600 = 133.3 个并发会话

反过来，如果你只能开 S 个沙箱，最大吞吐就是 S / 平均时长。并发上去以后，还有三个约束要一起看：推理端能不能装下这么多条上下文（KV cache）、生成吞吐够不够、下游工具扛不扛得住。

默认值和第 3 节一致：一条轨迹 20 回合、平均 240 秒，最终上下文 20 × 1400 = 28,000 token，按线性增长平均占用约一半，即 14,000。每个推理副本 500 万 token 的 KV 容量取自 AgentCore RL Toolkit 报告里的例子（Qwen3 Coder 30B 在一个 p6 节点上约 5M token，按 64K 上下文只能放 78 条轨迹），换模型、换硬件都要重新测。生成吞吐 10,000 token/秒是示例假设。下游工具 QPS ≈ 并发数 × 每回合工具调用数 / 每回合时长 = 133.3 × 1 / 12 ≈ 11 次/秒：如果工具是一个限流 10 QPS 的内部 API，这里就已经超了。

用公开数字核对一下量级：SageMaker AI 多轮 RL 的 Wordle 博客里，100 步训练共 105,486 条 rollout，用时 12 小时 40 分钟，平均约每小时 8,300 条。博客没有给出平均单条时长；假设一局平均 1 分钟，按 Little 定律平均约有 139 个会话同时在跑。同一篇博客也提到，他们在 32 个并发 rollout 时就遇到了凭证提供方被打满的问题（见第 8 节）。

8. Rollout 的可靠性

上千条并发轨迹里，总会有超时、崩溃、限流和环境故障。规则只有一条主线：每条 rollout 都要在有限时间内结束，并且返回一个奖励。

  • 超时分层：单次工具调用、单回合、整条轨迹各设上限。整条轨迹的上限也决定了第 4 节的长尾截断位置。AgentCore Runtime 的同步请求最长 15 分钟，microVM 上的异步任务最长 8 小时，会话默认空闲 15 分钟后终止（可调）；AgentCore RL Toolkit 因此让入口立即返回一个 S3 key，智能体在后台跑完，训练端用 HEAD 请求轮询 S3 拿结果，不用为长轨迹一直挂着 TCP 连接。
  • 永远返回奖励：SageMaker AI 多轮 RL 博客记录了两个坑：一条 rollout 从头到尾没有调用到策略模型，服务会以“No sampling requests were received”让整个训练任务失败；返回错误状态也会让任务失败。他们的做法是总返回一个奖励：模型被调用了但始终没给出有效猜测，就给最低分 −1.5（10 万多条 rollout 里有 51 条）。
  • 区分“模型的错”和“环境的错”：工具超时、沙箱崩溃这类环境故障如果也给最低分，模型会因为基础设施问题被惩罚。更稳妥的做法是在调度器里重试，或者把这条轨迹标记为无效、从组里剔除，并单独统计故障率（第 05 课第 6.1 节的诊断顺序）。具体用哪种，要看你的框架是否允许组大小可变。
  • 隔离与复位：每条轨迹独立的文件系统和状态。AgentCore Runtime 每个会话一个 microVM，CPU、内存和文件系统隔离，会话结束后 microVM 被终止、内存被清理；单会话最多 2 vCPU / 8 GB，会话存储最多 1 GB。需要更重的环境时，AgentCore RL Toolkit 的 Sandbox SDK 可以把命令和验证器放到单独的沙箱会话里执行，验证用的测试在智能体结束前不暴露给它。
  • 下游限流：按第 7 节估算的 QPS 给每个下游服务设并发上限和退避重试；训练时尽量用本地模拟或快照数据库代替真实服务（第 10 课的实验就是这样设计的）。凭证也会被并发打满：SageMaker 博客里，每次调用都新建 botocore 会话来生成 token，在 32 个并发 rollout 时拖垮了凭证提供方；把 token 缓存一小时又会在凭证轮换后返回 403。修复是共用一个能自刷新的会话、短缓存、遇到 403 重新签名。
  • 训练期间不要重新部署智能体：SageMaker 博客提醒，重新部署会重启 runtime，进行中的 rollout 收不到采样请求，整个任务失败。

为什么单条失败率要压得很低：GRPO 按组计算优势，一组 G 条里只要有一条失败需要处理，这一组就受影响。单条失败率 p 时，一组全部正常的概率是 (1 − p)G：

Rollout 网关 + 训练后端接入AgentCore RL Toolkit（开源，Apache-2.0）网关对智能体暴露 OpenAI / Anthropic 兼容接口，记录采样得到的 token id、logprob 和 loss mask；用 API key 字段里的会话 key 把多次调用归成轨迹。训练后端可选 verl、slime、SkyRL、Tinker 和 SageMaker Training Sessions。RolloutClient 提供并发控制、超时和会话清理。智能体代码通常只需换一个装饰器（@app.rollout_entrypoint）。

自建训练集群Amazon SageMaker HyperPod（可用 Amazon EKS 编排）或 Amazon EKSHyperPod 提供长时间运行、有故障恢复能力的 GPU 集群，可以挂到 EKS 控制面上。在上面自己运行 verl 或 slime，rollout 仍交给 AgentCore Runtime。AgentCore RL Toolkit 的 verl 指南列出的前提：一个 GPU 集群、能调用 AgentCore Runtime 和停止会话的 AWS 凭证、AgentCore 容器到训练节点网关端口的网络路由。

上表只列出了 AWS 文档和官方博客中写明的内容。配额和价格会变，以当前文档为准；没有写明的项目（例如具体实例型号的带宽）请按第 6 节自己测。

11. 小测验

为什么 rollout 沙箱通常不和训练放在同一批 GPU 机器上？
正确答案 C。这也是 AWS 用 AgentCore Runtime 承载 rollout、GPU 只做推理和训练的原因。
同步模式下，把每步的轨迹数从 64 增加到 1024（单条轨迹时长分布不变），rollout 阶段会怎样？
正确答案 B。最大值随 N 增长（对数正态下大致与 exp(σ·√(2 ln N)) 同阶）。第 4 节默认 σ = 0.5 时，最慢 / 平均从 N = 32 的约 2.6 增加到 N = 1024 的约 4.6。
目标每小时完成 3600 条轨迹，平均每条 5 分钟。按 Little 定律，平均需要多少个并发会话？
正确答案 A。3600 条/小时 = 1 条/秒，乘以 300 秒 = 300 个并发会话。实际还要加上长尾和重试的余量，再对照 AgentCore 的活跃会话配额和推理端的 KV 容量。
AReaL 把最大陈旧度 η 设为 0 时，系统的行为是？
正确答案 C。论文明确写了 η = 0 时退化为同步 RL。第 5 节把 k 拖到 0 可以看到：全部 token 同策略，但 rollout 槽利用率只有约 28%。
