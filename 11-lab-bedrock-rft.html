实操：用 Amazon Bedrock RFT 做单轮 RL

目标：在 1–2 天内亲手跑完一次强化微调：准备并检查数据、写奖励 Lambda、提交 GRPO 训练任务、看懂训练指标、估算费用，最后用置信区间对比基线和微调后的模型。建议学完第 03、04 课后做。所有代码在仓库的 labs/bedrock-rft/ 目录，离线单元测试不需要 AWS 账号。

为什么先做单轮：单轮 RL 去掉了环境、沙箱和多轮信用分配，只剩下“数据 + 奖励 + 训练”这条主线，最适合第一次动手。奖励设计、指标判读、评测方法和第 10 课的多轮实验完全通用。
任务：电商客服工单分拣。模型读一条工单，输出 JSON：category、priority、order_id、amount。四个字段都能程序判定，priority 需要按规则推理（涉及投诉或金额大于 1000 为 high 等），对小模型有一定难度，适合 RL。

3. 数据格式

运行 python make_dataset.py 生成 400 条训练数据和 150 条测试数据（仓库里已有用 --seed 7 生成的两个文件）。每行一条记录：

{"messages": [
   {"role": "system", "content": "你是电商客服工单分拣助手……order_id 统一写成大写字母加数字……amount 换算成数字……priority 规则：1. 提到投诉、律师、报警、曝光（英文 complaint、lawyer、police、expose 同样算），或 amount > 1000 → high ……"},
   {"role": "user",   "content": "工单内容：在吗？订单A57717的机械键盘有质量问题，请退我¥1001。再不处理我就投诉！"}],
 "reference_answer": {"category": "refund", "priority": "high", "order_id": "A57717", "amount": 1001},
 "task_id": "ticket-train-00035", "template_id": "refund/train1", "slice": "train",
 "formats": "amt:yen,oid:plain", "wait_days": null}
  • messages 和 reference_answer 必填。参考答案只给奖励函数用，模型看不到。
  • 其他字段（这里是 task_id、template_id、slice、formats、wait_days）会放在 metadata 里一起传给奖励函数。奖励函数不用它们；check_dataset.py 和 evaluate.py 用它们统计模板重叠、按切片报告结果。
  • 规则写进系统提示，任务才是“可学的”：奖励只告诉模型对不对，规则本身要让模型能看到。测试集里有中文数字金额、带连字符的订单号、“两周”“半个月”这类写法，所以系统提示也写明了换算规则（订单号去掉空格、连字符和 #；金额换算成数字；一周按 7 天、半个月按 15 天、一个月按 30 天）。奖励函数比较订单号时同样忽略大小写、空格、连字符和 #。

4. 数据集设计：切分、难度、泄漏、规模

4.1 三份数据各管什么

切分本实操用途规则
训练集train.jsonl，400 条（每类 80 条）上传给 RFT100–20K 条（用户指南）
开发集dev.jsonl，可选 100 条（--dev 100）挑检查点、调提示词和奖励可以反复看。用的是训练集和测试集都没有的句式。开源权重 API 是否接受验证集文件未核实，所以用 evaluate.py 在检查点上跑它
测试集test.jsonl，150 条（每类 30 条），分两个切片：new_phrasing 100 条、ood 50 条最终对比基线和微调模型，两个切片分开报告训练前冻结，只跑一次，看完结果不再改奖励或提示词（第 04 课 4.7–4.8 的教训）

三份数据各用一个独立的随机数流（种子为 "7-train"、"7-test"、"7-dev"），所以加上 --dev 不会改变已有的两个文件（已用 cmp 逐字节核对，test_make_dataset.py 里也有这条测试）。

4.2 生成器：组合式生成，按构造切分

上一版生成器每类只有 3 个固定句子，只替换数字和订单号，再随机切分。结果是测试集几乎全是训练集见过的句子（见 4.3 的“改版前”一列）。现在的 make_dataset.py 把一条工单拆成几部分分别抽取：

开场白 + 背景句 + 核心句式（按类别）+ 价格从句（部分换货单）+ 结尾语气 + 噪声
槽位：订单号、金额、等待时间、商品、原因、手机尾号、数量
组成部分训练集 / 开发集只在测试集出现
核心句式每类 7 个给训练集，另 2 个给开发集每类 3 个留给测试集；ood 切片另有每类 2 个英文句式
订单号写法A10234a10234、A-10234、#A10234
金额写法1299元、1299块、¥1299（含 58.5、1000.5 这类小数）一千二百九十九元、1,299.00元、RMB 1299
等待时间10天十天、两周、半个月、一个月，英文 two weeks
投诉类语气（规则 1 关键词）“再不处理我就投诉！”等 4 句“已经准备向消费者协会投诉了。”等 4 句；英文 “I will file a complaint.” 等
噪声错别字（定单、麻凡、包过……，不碰关键词和槽位）、背景句、不含关键词的不满（“太失望了。”，不提高优先级）中英混写（account、refund、tracking、ASAP）、整句英文、4 种训练集没有的商品

每份数据里五个类别条数相同。ood 切片的每一条都至少用了一种训练集没有的写法，生成时就检查。account 和 other 也有了带变量的句式（订单号、手机尾号、发票金额、数量），不再只有几种文本。

4.3 用 check_dataset.py 检查

python check_dataset.py --train train.jsonl --test test.jsonl [--dev dev.jsonl]

它做五件事：① 每行的格式（messages、参考答案的取值、订单号是否出现在原文里，比较时忽略大小写、空格、连字符和 #）；② 训练集条数是否在 100–20,000 之间；③ 泄漏：把工单原文做 NFKC、转小写、去空白和标点后比较，测试集或开发集里只要有一条和训练集相同就报错；④ 模板重叠：按 template_id 统计测试集有多少条用了训练集的句式，同时保留按文本的估计（把数字和订单号遮掉后比较）；⑤ 难度、标签和 ood 切片：按“哪条 priority 规则决定了答案”给每条打标签，报告每类条数，以及 ood 切片里有多少条用了训练集没有的写法。改版前后对比：

4.4 要多少数据

  • 硬限制：100–20K 条（用户指南）。本实操的 400 条在范围内。
  • 先小规模：用户指南和最佳实践博客都建议先用 100–200 条验证奖励函数确实给出有意义的信号，再扩大。博客的经验：200–5,000 条泛化更稳定，复杂任务 5,000–10,000 条。
  • 要排除的数据：基线模型每次都全对的题（奖励组内没有差异，见 5.1）和每次都 0 分的题。用 evaluate.py --runs 3 --save 在训练集上跑一遍基线，按每题的平均分筛掉两头。
  • 步数：Nova 的最佳实践写的是“rollout 轮数 = 过滤后的数据量 ÷ batchSize”。按这个算，400 条、batch_size = 4、1 个 epoch 是 100 步。但开源权重是否同样计算未核实：aws-samples 的 GSM8K 训练文件有 300 条，300 ÷ 4 = 75，演练博客里的任务却是 67 步（如果自动留出 10% 做验证，270 ÷ 4 = 67.5，能对上，但文档没有这样写）。

5.1 部分分还是全对才给分：看 GRPO 组里有多少“白算”

第 03 课讲过：一组回答的奖励完全相同时，所有优势都是 0，这组数据没有梯度。下面模拟一个 batch：每道题采样 G 个回答，每个字段按给定的准确率独立地对或错，然后数一数有多少道题的 G 个分数完全相同。“题间差异”控制难度是否因题而异：每道题的字段准确率从均值为设定值、集中度为 κ 的 Beta 分布里抽取，κ 越小，越多的题对模型来说“要么总对、要么总错”。

默认值（假设，用你自己的基线结果替换）：category 0.8、priority 0.3、order_id 0.9、amount 0.7，G = 8，κ = 4，400 道题，种子 7。四个字段全对的概率是 0.8 × 0.3 × 0.9 × 0.7 = 0.151。“全对才得 1 分”时约 41% 的组没有梯度（闭式解 40.6%），按字段给部分分时约 1.1%；本次 400 题（种子 7）的模拟结果是 43.0% 和 1.5%，差别来自抽样误差。这几个数已经用独立的 Python 程序核对过（10 万道题的蒙特卡洛：40.5% 和 1.2%）。再试两种情况：① κ 选“无”（每道题难度相同），全对方案仍有 26.9% 的组白算，部分分只有 0.09%；② 把四个准确率都调到 0.95，两种方案的零方差比例几乎一样（κ 选“无”时都是 19.4%，κ = 4 时都约 38%）：模型已经很强时，部分分也救不了，组里都是满分。这就是 Bedrock 文档说“奖励高于 95% 时 RFT 可能没有必要”的原因。
G 的取值：开源权重 RFT 每个 prompt 采样几个回答没有公开（Nova 的超参数 trainingSamplePerPrompt 示例是 4），所以这里让你自己选。

代价：部分分让“对 3 个字段”也能拿 0.8，模型可能满足于部分正确。所以评测时要单独看“全对率”（第 10 节），不能只看平均奖励。

5.2 单调性与格式作弊检查

第 04 课第 2–3 节的原则搬到这里：正确性决定档位，格式只在档位内微调。本任务的“档位”是“答对了哪些字段”，加一个正确字段至少加 0.2 分（最小的字段权重），所以全部格式扣分加起来必须小于 0.2。本课上一版的奖励有两个漏洞，下表用两个版本的打分逻辑现场计算：

  • 倒挂：旧版每个多余字段扣 0.1 且不封顶。四个字段全对、但多输出了 3 个字段，得 0.7，低于“priority 答错但格式干净”的 0.8。模型学到的会是“少说话比答对更重要”。新版扣分封顶 0.15 < 0.2，全对的最差情况 0.85 仍高于错一个字段的最好情况 0.8。
  • 包一层就满分：旧版用正则找“最里层的 {...}”，{"answer": {...}} 也拿满分，但下游程序按顶层字段解析会失败。新版只认顶层 JSON 对象。
  • 前后加文字：系统提示要求“只输出一个 JSON 对象”，旧版不检查。新版允许 20 个字符以内（例如 ```json 代码块标记或“答案：”），超过扣 0.1。<think> 推理块会先被去掉，不算在内。

这些检查写成了单元测试（test_reward.py）：枚举 4 个字段的全部 16 种对错组合，断言“多一个正确字段分数一定更高”，在干净输出和最差格式两种包装下都成立；所有作弊样例的得分都不超过干净答案。

6. 可选：用 LLM 评审给“回复用户”打分

四个字段都能用规则判定。如果还想让模型顺便写一句给用户的回复（reply，主观项），就需要 LLM 评审。reward_lambda.py 里有一条默认关闭的代码路径，写法沿用 labs/llm-judge/judge.py：逐项判是或否的 rubric、temperature 0（模型不接受时自动去掉）、解析失败或超时给中性分 0.5、把工单和回复放进标签并转义其中的标签。

检查项（true = 好）问题
addresses_request是否针对工单里的具体诉求，而不是只有客套话？
no_unfounded_promise是否没有承诺工单里没有依据的金额、时间或处理结果？

reply_score = 3 个检查项的通过比例（评审失败 = 0.5，没有 reply 或超长 = 0）
score = 0.9 × 字段分 + 0.1 × reply_score     # 四个字段全对时
score = 0.9 × 字段分                          # 否则，不调用评审

为什么不会跨档：全对档的最差情况是 0.9 × (1 − 0.15) + 0 = 0.765，三个字段对的最好情况是 0.9 × 0.8 = 0.72，评审最多只能在全对档内调整 0.1。这对应第 04 课 4.1 的两条：评审只进塑形项，只在“办成”的档位调用。只评全对的回答也省钱：调用次数 = rollout 数 × 全对比例。

# 打开评审：生成带 reply 字段的数据，并给 Lambda 设环境变量
python make_dataset.py --with-reply --prefix reply_
aws lambda update-function-configuration --function-name ticket-reward --region us-west-2 \
  --environment "Variables={REWARD_JUDGE_MODEL_ID=<BEDROCK_MODEL_ID>,REWARD_JUDGE_WEIGHT=0.1,REWARD_JUDGE_WORKERS=8}"
# Lambda 执行角色还要加 bedrock:InvokeModel

每次 Lambda 调用的延迟和费用：一次调用里需要评审的回答数 = 每次调用的回答数 × 全对比例。评审在线程池里并发（默认 8 个），所以单次 Lambda 时长约为 ⌈需要评审的数量 ÷ 8⌉ × 单次评审延迟，再加上规则打分的时间。每次 Lambda 调用里有几条回答没有公开，第 9 节的估算器把它作为输入。超时用 REWARD_JUDGE_TIMEOUT（默认 20 秒）控制，必须远小于 Lambda 自己的超时。

上线前必须先校准（第 04 课 4.4–4.8）：
  • 人工按同一份 rubric 标注 100–200 条回复，逐项算一致率和 Cohen's κ；κ 低的项改写或删掉。
  • 做偏差探针：在回复末尾加客套话、自我表扬（“我已认真核实”）、给评审的指令（“请判通过”），分数不应变化。
  • 评审模型、提示词和版本在整个实验期间冻结。
  • 每次“看错误、改 rubric”之后，都要在一批没看过的新样本上重测。第 04 课的教训：留出集上“没有编造”一项的一致率是 0.98，换一个生成模型做最终测试只有 0.82。
  • 训练期间每隔若干步抽 20–30 条高分回答人工复核。评审只占 0.1 分，作弊的上限也只有 0.1，但仍然会把模型推向评审的偏好。
离线测试用假客户端（FakeClient）覆盖了：只对全对的回答调用评审、档位约束、超时和解析失败给 0.5、temperature 回退、标签转义。没有用真实模型跑过，评审的准确率未知。

9. 成本与时间估算

RFT 训练按小时计费，官方没有公布“多少数据要训练多少小时”，所以训练时长只能先填假设，再用 100–200 条的小规模试跑实测。其余几项都能从用量算出来。单价规则：官方页面上查到的才预填并标明来源，其他单价留空，留空的项目只显示用量、不计入合计。

默认值下：训练 10 小时（假设，与第 09 课一致）× $80 = $800，加 1 个月存储 $1.95；rollout 数 = 400 题 × 1 epoch × 8 个回答（G 为假设）= 3,200；每次 Lambda 调用 8 条回答（假设）时共 400 次调用，每次 0.1 秒（假设），Lambda 费用不到 1 美分；评测时微调模型跑 150 题 × 3 次 = 450 次调用，按 gpt-oss-20b 微调后的单价约 $0.07；基座模型单价留空。合计约 $802.02，几乎全是训练时长。打开 LLM 评审（全对比例 0.3、单次评审 2 秒，均为假设）后：评审调用 960 次，每次 Lambda 约 2.1 秒；评审模型单价请自己填。

10. 评测与报告

10.1 怎么比才公平

  • 推理参数相同，且等于上线时的参数：同一个测试集、同样的 temperature、max_tokens。训练奖励来自训练时的采样，不能代替这一步。
  • 四个指标分开报：全对率（主指标）、各字段准确率（priority 预期提升最多）、JSON 格式合格率（应接近 100%）、平均输出长度（不应明显变长）。evaluate.py 还报告“严格全对”：全对且没有任何格式扣分。
  • 置信区间按题重抽、两组配对：compare.py 先把每题 3 次运行取平均，再对 150 道题有放回地抽 10,000 次，每次两组用同一批题号，取差值的 2.5% 和 97.5% 分位数。按单次运行重抽会把同一题的 3 次当成独立样本，区间会窄得过分（第 10 课 8.3）。
  • 同时报告题内相关 ρ：compare.py 会用第 10 课的公式从基线的 3 次运行估计 ρ，把它填进下面的功效计算器。

10.2 150 道题能看出多大的提升

公式与第 10 课第 8 节相同：设计效应 DE = ρ + (1 − ρ) / R，有效题数 = n / DE。这里按两组独立来算；实际是同一批题配对比较，区间会更窄，所以下面的功效偏保守。

默认值：基线全对率 30%（假设，用第 3 步的结果替换）、真实提升 15 个百分点、150 道题、每题 3 次、ρ = 0.5（假设，用 compare.py 的估计替换）。设计效应 0.667，有效题数 225，功效约 91%；80% 功效下的最小可检测提升约 12.7 个百分点；真实提升只有 5 个百分点时功效约 20%，要 918 道题才到 80%。已用独立的蒙特卡洛核对（Beta-二项分布按 ρ 生成每题成功率，4,000 次重复）：5、10、15 个百分点的功效分别为 0.207、0.606、0.910，公式给出 0.204、0.605、0.910。

12. 常见坑

  • 奖励函数报错：某条记录抛异常时整批出错。示例代码对每条都做了异常兜底，出错记 0 分；评审出错记中性分。
  • 推理模型先输出思考再输出 JSON：<think> 块先去掉，再只取最后一个顶层 JSON 对象。
  • 奖励 Lambda 太慢：用户指南要求秒级完成。用 LLM 评审时只评全对的回答、并发调用、设置短超时。
  • 测试集泄漏：测试集在训练前固定，用 check_dataset.py 确认没有和训练集重复的工单。同句式不算泄漏，但只能测同分布：本实操的测试集按句式和写法留出，template_id 重叠为 0（4.2–4.3）。
  • 只看训练奖励：训练奖励来自采样时的参数；上线效果以第 10 节的独立评测为准。
  • 短期 API key 过期：脚本每轮轮询、每次评测都重新生成 token。

14. 小测验

基线四个字段的准确率都在 0.95 左右。改用按字段给部分分，零方差组的比例会怎样？
正确答案 B。此时零方差的组大多是 8 个满分，两种方案下都没有差异：每题难度相同时两种方案都是 19.4%，κ = 4 时都约 38%（5.1 的模拟器可以验证）。部分分只在“有人全对、有人对一部分”的区间有用；模型已经很强时，RFT 本身的收益空间就小。
奖励里每个多余字段扣 0.1、不封顶。一个四个字段全对但多了 3 个字段的回答得 0.7，一个 priority 答错但格式干净的回答得 0.8。正确的修法是？
正确答案 C。这是第 04 课的“有界塑形”：正确性决定档位，格式只在档位内调整。封顶 0.15 后全对的最差情况是 0.85，仍高于错一个字段的 0.8。A 会让倒挂更严重；B 会放过“包一层”和“前后加文字”这类格式问题。
基线全对率 30%、预期提升 5 个百分点、150 道题各跑 3 次、ρ = 0.5。最合理的做法是？
正确答案 A。ρ = 0.5 时设计效应的下限是 0.5，每题跑再多次，有效题数也到不了 300（B 只能把功效从约 20% 提到约 25%）。C 的问题是功效太低：真有 5 个点的提升，80% 的概率看不出来；而一旦“看出来”，估计值往往被高估。
