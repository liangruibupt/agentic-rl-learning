实操：用 Amazon Bedrock RFT 做单轮 RL

目标：在 1–2 天内亲手跑完一次强化微调：准备数据、写奖励 Lambda、提交 GRPO 训练任务、看懂训练指标、对比基线和微调后的模型。建议学完第 03、04 课后做。所有代码在仓库的 labs/bedrock-rft/ 目录。

为什么先做单轮：单轮 RL 去掉了环境、沙箱和多轮信用分配，只剩下“数据 + 奖励 + 训练”这条主线，最适合第一次动手。奖励设计、指标判读、评测方法和第 10 课的多轮实验完全通用。
任务：电商客服工单分拣。模型读一条工单，输出 JSON：category、priority、order_id、amount。四个字段都能程序判定，priority 需要按规则推理（涉及投诉或金额大于 1000 为 high 等），对小模型有一定难度，适合 RL。

3. 数据格式

运行 python make_dataset.py 生成 400 条训练数据和 150 条测试数据。每行一条记录：

{"messages": [
   {"role": "system", "content": "你是电商客服工单分拣助手……priority 规则：1. 提到投诉、律师、报警、曝光，或 amount > 1000 → high ……"},
   {"role": "user",   "content": "工单内容：订单A10234的商品有质量问题，请退我1299块钱。再不处理我就投诉！"}],
 "reference_answer": {"category": "refund", "priority": "high", "order_id": "A10234", "amount": 1299},
 "task_id": "ticket-00042"}
  • messages 和 reference_answer 必填。参考答案只给奖励函数用，模型看不到。
  • 其他字段（如 task_id、difficulty）会放在 metadata 里一起传给奖励函数。
  • 规则写进系统提示，任务才是“可学的”：奖励只告诉模型对不对，规则本身要让模型能看到。

5. 操作步骤

第 1 步 · 环境 
pip install openai boto3 aws-bedrock-token-generator
cd labs/bedrock-rft
python make_dataset.py --train 400 --test 150
python -c "import test_reward as t; [getattr(t,n)() for n in dir(t) if n.startswith('test_')]; print('ok')"
先跑奖励函数的单元测试。奖励写错了，后面的训练全部白费。
第 2 步 · 部署奖励 Lambda 
zip reward.zip reward_lambda.py
aws lambda create-function --function-name ticket-reward \
  --runtime python3.12 --handler reward_lambda.lambda_handler \
  --zip-file fileb://reward.zip --timeout 300 --memory-size 512 \
  --role arn:aws:iam::<ACCOUNT>:role/<LAMBDA_EXEC_ROLE> --region us-west-2
超时设为 5 分钟、内存 512 MB（与 AWS 博客一致；Lambda 默认 3 秒超时太短）。还要让 Bedrock 有权限调用这个函数，按用户指南 “Lambda permissions for reward functions” 一节配置。部署后用一条测试事件调用，确认返回 [{"id": ..., "aggregate_reward_score": ...}]。
第 3 步 · 测基线 
python evaluate.py --model openai.gpt-oss-20b --runs 3
记录平均奖励、全对率、每个字段的准确率。判断要不要继续：全对率接近 0，先改提示词或做 SFT；高于 95%，RL 意义不大（Bedrock 最佳实践）。
第 4 步 · 提交训练 
python run_rft.py --lambda-arn arn:aws:lambda:us-west-2:<ACCOUNT>:function:ticket-reward \
  --epochs 1 --batch-size 4 --lr-mult 0.5
脚本会上传数据、创建任务，然后每分钟打印一次训练指标。核心调用：
job = client.fine_tuning.jobs.create(
    model="openai.gpt-oss-20b",
    training_file=file_id,
    extra_body={"method": {"type": "reinforcement", "reinforcement": {
        "grader": {"type": "lambda", "lambda": {"function": lambda_arn}},
        "hyperparameters": {"n_epochs": 1, "batch_size": 4, "learning_rate_multiplier": 0.5}}}})
第 5 步 · 看训练指标：见下一节的诊断实验台。
第 6 步 · 评测微调后的模型 
python evaluate.py --model <FINE_TUNED_MODEL_ID> --runs 3
任务成功后，client.fine_tuning.jobs.retrieve(job_id).fine_tuned_model 就是模型 ID，可以直接按需调用，不需要部署端点。和基线用同一个测试集、同一个 temperature 对比。
第 7 步 · 清理：删除 Lambda 函数和上传的文件。微调后的模型不调用就不产生推理费用；存储与托管费用以定价页为准。

6. 动手：看懂训练指标

训练事件里每一步都有这些指标：critic_rewards_mean（批次平均奖励，最该看）、actor_entropy（输出多样性）、response_length_mean（平均回复长度）、actor_grad_norm（梯度大小）。选一种情况，看曲线长什么样、该怎么处理：

奖励（训练 / 验证）
策略熵
平均回复长度

曲线为示意，用来说明形态。作为参考，AWS 博客中 gpt-oss-20B 在 GSM8K 上的 RFT 共 67 步，平均奖励从约 0.56 升到 0.85–0.97，回复长度逐渐变短。

7. 实验记录表

指标基线RFT 后判定
平均奖励（3 次均值）提升，且 3 次之间的波动小于提升幅度
全对率（四个字段都对）主指标
priority 准确率最需要推理的字段，预期提升最多
JSON 格式合格率应接近 100%
平均输出长度不应显著变长

进阶实验（任选）：① 把奖励改成“全对才得 1 分”，对比学习速度；② learning_rate_multiplier 分别取 0.25、0.5、1.0；③ 在测试集里加入训练中没有的工单写法（例如英文工单），看泛化。

8. 常见坑

  • 奖励函数报错：某条记录抛异常时整批出错。示例代码对每条都做了异常兜底，出错记 0 分。
  • 推理模型先输出思考再输出 JSON：只取最后一个 JSON 对象，并忽略思考块。
  • 奖励 Lambda 太慢：Bedrock 建议秒级完成。需要 LLM 评审时，注意 Bedrock 调用的并发和延迟。
  • 测试集泄漏：测试集要在训练前固定，并且不要和训练集共用同一批工单原文。
  • 只看训练奖励：训练奖励来自采样时的 temperature；上线效果以第 6 步的独立评测为准。
