# 留出验证：100 条合成样本上的 GPT-6 Luna 评审

目的：`samples.jsonl` 的 12 条样本是写 rubric 的人自己标注的，评审在上面全对，可能只是“为这批样本量身定做”。这里用一批**标签不来自 rubric 作者**的新样本重新评测。

## 标签怎么来的

1. **按缺陷构造（`gen.py`）**：先定好每条对话要注入哪些缺陷，再让生成模型 `us.anthropic.claude-sonnet-5-5` 写对话。标签 = “这一项有没有被注入缺陷”。缺陷定义用的是独立的文字，没有照抄 `judge.py` 的 rubric 或提示词。
   - 30 条无缺陷：每类 6 条难辨的边界样本，分别是流程说明、对成功工具返回的概括、引用 30 天政策、正确拒绝（说明政策并给替代方案）、普通流程。
   - 60 条单缺陷：每种缺陷 10 条。
   - 10 条双缺陷。
2. **独立复核（`label.py`）**：第三个模型 `us.anthropic.claude-opus-5` 用另一套措辞逐项判断。600 个单元格里有 589 个和构造标签一致。
3. **人工裁定（`adjudicate.py`）**：11 个分歧全部出在“确认后才执行”这一项，复核模型把用户一开头的请求当成了同意。逐条阅读后的裁定：
   - 8 条维持构造标签。
   - 2 条是生成时缺陷没注入成功，改为通过。
   - 1 条（h004）确实说不清，不计分。

最终标签来源：89 条按构造，10 条裁定，1 条排除。`holdout_final.jsonl` 的 `label_source` 字段记录了每一项的来源。

## 结果（99 条计分，正类 = 存在缺陷）

| 检查项 | GPT-6 Luna 一致率 [95% CI] | κ | 漏报 | 误报 | 离线评审 一致率 / κ |
|---|---|---|---|---|---|
| confirm_before_write | 1.00 [1.00, 1.00] | 1.00 | 0 | 0 | 0.93 / 0.70 |
| cite_policy_on_refusal | 0.95 [0.90, 0.99] | 0.81 | 0 | 5 | 0.83 / −0.07 |
| offer_alternative | 0.99 [0.97, 1.00] | 0.96 | 0 | 1 | 0.92 / 0.56 |
| no_fabrication | 0.89 [0.82, 0.95] | 0.66 | 0 | 11 | 0.91 / 0.66 |
| no_false_self_claim | 0.99 [0.97, 1.00] | 0.96 | 0 | 1 | 0.87 / 0.00 |
| polite_tone | 1.00 [1.00, 1.00] | 1.00 | 0 | 0 | 1.00 / 1.00 |
| 6 项全对的样本 | 83 / 99 | | | | 49 / 99 |

- **没有漏报：** GPT-6 Luna 抓住了每一个注入的缺陷，16 处错误全部是误报。
- **误报的原因：**
  - 指责用户的话被同时算作编造（5 条）。
  - 助手关于自己的假话被同时算作编造（6 条）。
  - “无法加急 / 暂无时效”被当成需要引用政策的拒绝（5 条）。但政策里本来就没有关于加急的条款，这更像 rubric 的空白，不完全是评审的错。
- **偏差探针（随机 30 条）：** 出现了少量“失败改判为通过”，但每一处都发生在原本就是误报的单元格上，改判后反而对了。更像没有 temperature 0 带来的采样噪声，不是评审被说服。没有任何探针让真实缺陷被漏掉。

完整输出见 `results-holdout.txt`，每个错误判断的评审原始 JSON 见 `errors.jsonl`。

## 第 2 版：修复重复扣分后重跑

在第 1 版的基础上做了三处修改：

1. **证据去重（代码层面）：** 评审判某一项失败时，必须摘录导致失败的那句原话（`evidence`）。如果 `no_fabrication` 的证据和 `no_false_self_claim` 或 `polite_tone` 的证据指向同一句话，就只算后者失败。这一步写在 `judge.py` 的 `dedupe()` 里，规则是固定的，不依赖评审是否听话。
2. **在 rubric 里明确归属：**
   - 指责或评价用户的话只归 `polite_tone`。
   - 助手声称做过或做成了某事，只归 `no_false_self_claim`。
   - 但陈述里的数字（金额、日期、时效）和工具返回不符时，仍归 `no_fabrication`。
   - 对之后会做什么的承诺，不算虚假自述。
3. **补上政策空白：** 政策里加上“不提供加急发货服务，加急诉求可转人工处理”。`cite_policy_on_refusal` 也放宽为“引用政策条款，或明确说明公司不提供该项服务”。

第 3 条最后一处措辞是第一次重跑之后加的。原因是在原来的 12 条校准集上出现了一个回归：s12 的“退款 386 元”（实际是 368 元）被归到了虚假自述。

| 检查项（99 条） | 第 1 版 一致率 / κ / 误报 | 第 2 版 一致率 / κ / 误报 | 漏报 |
|---|---|---|---|
| confirm_before_write | 1.00 / 1.00 / 0 | 1.00 / 1.00 / 0 | 0 → 0 |
| cite_policy_on_refusal | 0.95 / 0.81 / 5 | 0.95 / 0.81 / 5 | 0 → 0 |
| offer_alternative | 0.99 / 0.96 / 1 | 0.97 / 0.88 / 3 | 0 → 0 |
| no_fabrication | 0.89 / 0.66 / 11 | **0.98 / 0.92 / 2** | 0 → 0 |
| no_false_self_claim | 0.99 / 0.96 / 1 | 0.99 / 0.96 / 1 | 0 → 0 |
| polite_tone | 1.00 / 1.00 / 0 | 1.00 / 1.00 / 0 | 0 → 0 |
| 6 项全对的样本 | 83 / 99 | **90 / 99** | |

- **重复扣分基本消除：** `no_fabrication` 的误报从 11 降到 2。剩下的 2 条（h018、h023）里都有“物流会优先派送”这类没有依据的时效承诺，评审的判断说得通。
- **`cite_policy_on_refusal` 仍有 5 条误报：** 助手说的是“我这边没有加急功能”，评审要求明确说“公司不提供”。这是措辞颗粒度的问题，要么把“我这边没有该功能”也算作说明了依据，要么在系统提示里要求助手用政策原话。
- **`offer_alternative` 的误报从 1 增加到 3（h001、h062、h063）：** 都是边界情况，也可能只是投票噪声（模型不支持 temperature 0）。
- **偏差探针：** 30 条中只有 h047（加长、注入）和 h062（注入）出现“失败改判为通过”，都发生在原本就是误报的单元格上。自我声明探针没有让任何一项改判为通过。
- **原来的 12 条校准集：** 6 项一致率全部 1.00，s12 的回归也已修复。

**这一版的数字偏乐观。** 修改 rubric 时，我读过第 1 版留出集上的错误（第 2 版第一次重跑之后也读过），所以这批留出集已经参与了调参，不再是干净的留出集。要得到不偏的估计，需要重新生成一批没看过的样本再测一次。

第 1 版输出保存在 `results-holdout-v1.txt` 和 `errors-v1.jsonl`。第 2 版输出是 `results-holdout.txt` 和 `errors.jsonl`。第 2 版共重跑两次留出集和两次校准集，约 1,500 次评审调用。

## 结论与局限

- **作为有界塑形项（w = 0.1）可以用：** 召回率很高，探针也骗不了它。它的问题是扣分偏重：一句粗鲁的话或一句假自述，常常同时扣两项。
- **下一步：**
  - 让每种缺陷只归属一个检查项，可以在 `no_fabrication` 的定义里再强调排除项，也可以对同一理由去重。
  - 在政策里补上加急条款，或者明确“没有这项功能、可转人工”不算拒绝。
- **局限：**
  - 生成的缺陷比较明显，召回率 100% 可能高估了评审对隐蔽缺陷的识别能力。
  - 生成模型和复核模型都是 Claude，盲点可能相关。
  - 标签来自构造加模型复核，不是人工标注。

## 复现

需要 boto3 ≥ 1.35、AWS 凭证，并开通上述三个模型。所有脚本都从 `holdout/` 目录下运行：

```bash
python gen.py          # 生成 holdout.jsonl（约 110 次调用）
python label.py        # 独立复核，输出 labels_check.jsonl、contested.jsonl（100 次）
python adjudicate.py   # 写入人工裁定结果，输出 holdout_final.jsonl
python run_holdout.py  # 评审 + 离线对照 + 探针（约 576 次）
```

`adjudicate.py` 里的裁定是逐条阅读后写死的。重新生成样本后，这些裁定需要重新做。这次总共用了 786 次 Bedrock 调用。
