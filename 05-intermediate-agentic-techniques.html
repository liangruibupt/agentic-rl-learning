2. 信用分配

一条 20 回合的轨迹最终失败了，问题可能只出在第 3 回合查错了订单。轨迹级奖励会把 20 个回合“一起罚”，好的步骤也被罚了。解决思路：

  • 靠样本量平均：GRPO 默认做法。足够多的轨迹里，好步骤在成功轨迹中出现得更多，统计上会被区分出来。简单但样本效率低。
  • 回合级奖励：对能评分的中间步骤单独打分。SageMaker AI 多轮 RL 支持通过 UpdateReward 接口上报逐回合奖励。
  • 以回合为转移单位的算法：如 Agent-R1 等工作把每次交互作为 RL 的基本转移，可以做回合级优势估计。

3. 其他必须处理的技术点

训推一致（token 进、token 出）

智能体框架通常把消息列表交给模型 API，每轮重新套 chat template、重新分词。重新分词的结果可能和模型当初生成的 token 不一致，算出的 logprob 对不上，训练会悄悄跑偏。正确做法是在网关层记录采样时的原始 token id 和 logprob，训练直接使用。AWS 开源的 AgentCore RL Toolkit 的 rollout gateway 就是做这件事的。

上下文管理

多轮任务每轮都要重读历史，上下文快速膨胀。AWS 的 Wordle 实验中 prefill token 是生成 token 的 3 倍多，训练 token 成本占了总成本的大头。常见手段：截断旧的工具输出、摘要记忆、限制最大回合数。

冷启动

如果基础模型连工具调用格式都做不对，奖励全是 0，GRPO 没有梯度。Bedrock 文档建议：基线接近 0% 先做 SFT；高于 95% 则 RL 收益有限。常用做法是让前沿模型（例如 Bedrock 上的 Claude）跑出成功轨迹，用来做蒸馏 SFT，再上 RL。

格式漂移

学习率过高时，模型可能把工具调用写成纯文本，所有 rollout 拿同样的最低分，梯度消失。这是 SageMaker 博客记录的真实踩坑。对策：降低学习率；从纯文本中恢复工具调用并给小幅格式惩罚；监控“有效工具调用率”。

环境隔离与可复位

每条 rollout 要有独立的文件系统和状态，且能恢复到初始快照。上千条并发轨迹共享一个数据库，会互相污染。AgentCore Runtime 为每个会话分配独立 microVM，会话结束即销毁，适合承担这一层。

评测设置要和服务一致

训练任务的验证通常用 temperature 0，但上线可能用 1.0。AWS 的 Wordle 实验中，训练曲线显示最终 37%，按服务设置评测是 84%。永远按你实际上线的解码参数评测。
